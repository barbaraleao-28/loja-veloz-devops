# Parte teórica
## INTRODUÇÃO
A Loja Veloz precisa se preparar para uma campanha em que mais pessoas vão comprar ao mesmo tempo. Hoje, uma atualização pode interromper o site. Quando uma compra demora, a equipe também tem dificuldade para descobrir se o problema está no estoque, no pagamento ou no próprio atendimento ao cliente. Neste trabalho, a compra de um mouse serve de exemplo para acompanhar essas etapas e verificar o que acontece quando o sistema recebe mais acessos.
## ORGANIZAÇÃO DOS SERVIÇOS
Para o cliente, a compra é uma só. Dentro da loja, ela envolve quatro serviços. O primeiro, chamado API Gateway, recebe a solicitação. O serviço de Pedidos coordena as etapas. Estoque verifica se o produto está disponível e reserva a quantidade solicitada. Pagamentos devolve o resultado da autorização. No projeto, essa autorização é simulada. Quando o pagamento é aprovado, a compra fica registrada no PostgreSQL e a reserva é baixada.
Essa divisão é a base da arquitetura de microsserviços. Cada serviço tem uma responsabilidade e pode receber uma atualização própria, desde que continue a trocar informações no formato que os demais esperam. A divisão também traz uma dificuldade. Se a resposta do pagamento se perder, repetir a cobrança pode prejudicar o cliente. Para trabalhar com uma operadora real, a loja precisaria identificar cada tentativa e consultar seu resultado antes de cobrar novamente.
## O PAPEL DO DEVOPS
Na Loja Veloz, desenvolvimento e operação precisam acompanhar a mesma mudança. A equipe registra o código e as configurações no repositório, testa a compra e identifica a versão que vai publicar. Depois da atualização, acompanha os pedidos para verificar se o cliente ainda consegue comprar. Esse trabalho conjunto ajuda a encontrar uma falha enquanto ainda se sabe qual alteração pode ter causado o problema.
Como referência, foi utilizada a Online Boutique, aplicação de exemplo do Google Cloud. Nela, um serviço de checkout coordena etapas como pagamento e entrega. A mesma ideia orientou a separação entre a entrada da Loja Veloz e o serviço de Pedidos. Com quatro serviços, já é possível acompanhar a compra e identificar em qual etapa ocorreu uma falha.

## CONTAINERS E ATUALIZAÇÕES
Um container executa a aplicação com as bibliotecas de que ela precisa. O Docker permite construir uma imagem com esses arquivos. Com o Docker Compose, a equipe descreve os serviços, as conexões e os dados que devem ser preservados. Assim, quem recebe o projeto consegue iniciar o mesmo ambiente de desenvolvimento com um comando.
O Kubernetes atende a outra necessidade da loja. Ele mantém cópias dos serviços em funcionamento, encaminha as chamadas para as cópias disponíveis e substitui as que falham. Na atualização gradual, chamada RollingUpdate, uma nova cópia precisa estar pronta para atender antes que a antiga seja retirada. Essa escolha evita manter duas instalações completas durante toda a atualização e exige espaço para uma cópia adicional.
A integração e a entrega contínuas, conhecidas pela sigla CI/CD, organizam o caminho entre alterar o código e publicar uma versão. Se um teste de estoque falhar, por exemplo, o processo deve parar antes da publicação da imagem. Como duas versões podem funcionar juntas durante a troca, as mudanças nas tabelas do banco também precisam atender à versão que ainda está em uso.
## COMO ACOMPANHAR UMA COMPRA
As métricas ajudam a perceber um problema geral, como o aumento no tempo de resposta. Os logs registram o que um serviço fez em determinado momento. Já o rastreamento distribuído reúne as etapas de uma mesma compra por um identificador comum. Se o cliente reclamar de demora, a equipe pode abrir esse rastreamento no Jaeger e descobrir quanto tempo foi gasto em Estoque e em Pagamentos.
Também é importante separar a confirmação da compra do envio de avisos para outros serviços. A loja grava o pedido e o aviso de criação na mesma operação no banco. Se o Redis estiver fora do ar, o aviso fica pendente e pode ser enviado quando a conexão voltar. Se houver uma queda logo depois do envio, a mensagem pode chegar duas vezes. Por isso, quem recebe o aviso precisa verificar seu identificador antes de repetir uma ação.
